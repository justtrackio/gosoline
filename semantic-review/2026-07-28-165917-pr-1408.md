# Native OpenTelemetry for traces, metrics and logs

A new `pkg/otel` package centralizes the OTEL resource and the OTLP exporter builders (gRPC/HTTP, gzip, headers, retry, TLS/mTLS) so all three signals share identical resource attributes. On top of it, tracing gains `otel_grpc` and `stdout` exporters plus configurable propagators, metric gains an `otel` writer that bridges the existing `Datum` pipeline onto a `MeterProvider` with a `PeriodicReader`, and log gains an `otel` handler that emits through the OTEL Logs SDK batch processor. To make the batched exporters flush, the kernel grew a `ShutdownHandler` list plus an unconditional `logger.Close()` at exit, which forced `log.GosoLogger` to gain `Close` and the kernel builders to take `GosoLogger` instead of `Logger`.

Watch for: `gosoLogger.Close` returns `nil` on handler error and aborts the loop, so OTLP shutdown failures are invisible and later handlers never close (confirmed); the whole new exit sequence runs on `k.ctx` with no deadline, so a dead collector plus the default 300s retry budget can pin process exit — including on the `forceExit` kill-timeout path, which can no longer terminate a blocked shutdown (confirmed); flushing is opt-in via `application.WithOtelShutdown`, which is not in `Default()` and not implied by `WithTracing`/`WithMetrics`, so the common wiring registers providers that are never shut down (confirmed); `logger.WithChannel("kernel").(log.GosoLogger)` is an unchecked assertion that panics for any `GosoLogger` whose `WithChannel` returns a plain `Logger` (confirmed).

The PR description lists "explicit shutdown-flush hook" as a follow-up, but the diff implements it — the body needs an update so reviewers evaluate the shutdown path rather than skipping it.

## High-level view

Shutdown is where the risk concentrates. `kernel.exit()` now runs an ordered list of `ShutdownHandler`s and then closes the logger, all with the app context and no timeout. OTLP shutdown is a network flush with retry (`max_elapsed_time` default 300s), so an unreachable collector turns process exit into a multi-minute stall. `forceExit` — the path that exists precisely to escape a stuck shutdown — funnels through the same `exitOnce`, so a second SIGTERM cannot kill a process already blocked inside a shutdown handler.

The flush hook is opt-in. `metric.NewOtelWriter` and `newOtelTraceProvider` register their `Shutdown` funcs into appctx, but nothing invokes them unless the app adds `application.WithOtelShutdown` by hand. Apps that just use `WithTracing`/`WithMetrics` (the documented path) lose the final batch and leak the `PeriodicReader` goroutine. Log export is the exception: the kernel always calls `logger.Close()`.

`gosoLogger.Close` has an inverted error path (`return nil` inside the error branch). It both hides OTLP shutdown failures and stops closing the remaining handlers. The kernel's reaction to a close error — overwriting `exitCode` with `ExitCodeErr` — is currently unreachable for the same reason, and once the bug is fixed a flaky telemetry flush will start failing otherwise-successful runs.

The API surface moves in a way external code will feel: `BuildKernel`, `BuildFactory` and `NewFactory` now require `log.GosoLogger`, and `GosoLogger` gained `Close(ctx)`. Anyone implementing `GosoLogger` outside the repo breaks at compile time; anyone whose `WithChannel` returns a non-`GosoLogger` breaks at startup with a panic.

`pkg/otel/settings.go` reads cleanly but accepts several configurations that silently do the wrong thing: `port` defaults to 4317 regardless of `protocol: http`, an unrecognized `compression` value degrades to none, and a `cert_file` without `key_file` silently drops mTLS. There is no `Validate` step; `ReadSettings` only unmarshals. With `insecure: true` as the default and `headers` as the documented place for auth tokens, the default posture sends bearer credentials in cleartext.

Traces are the odd signal out. `NewOtelGrpcTracer` overwrites `Protocol` with grpc, and the tracing default exporter is still `otel_http` reading the legacy `tracing.otel.http.*` keys — so an operator who configures `otel.exporter.protocol: http` gets it honored for metrics and logs and ignored for traces.

Resource construction uses `resource.NewWithAttributes`, which skips `resource.Default()` and therefore drops `telemetry.sdk.*` and ignores `OTEL_RESOURCE_ATTRIBUTES`. Within the same function, a bad `service_name_pattern` errors out while a bad `service_namespace_pattern` is silently discarded.

Test coverage exercises the exporters but not the production wiring: the integration suite builds providers by hand, so `NewOtelWriter`, `handlerOtelFactory`, the kernel shutdown sequence and every TLS path are untested end to end. `TestKernelExitReportsLoggerCloseError` passes against a hand-written fake, which is exactly why the real `Close` bug survived.

### The exit sequence became a blocking network operation

`kernel.exit()` grew two responsibilities on top of calling the exit handler:

```go
func (k *kernel) exit() {
	k.exitOnce.Do(func() {
		k.logger.Info(k.ctx, "leaving kernel with exit code %d", k.exitCode)

		for _, handler := range k.shutdownHandlers {
			if err := handler.Shutdown(k.ctx); err != nil {
				k.logger.Warn(k.ctx, "shutdown handler completed with errors: %s", err)
			}
		}

		if err := k.logger.Close(k.ctx); err != nil {
			fmt.Printf("close logger completed with errors: %s\n", err)
			k.exitCode = ExitCodeErr
		}

		k.exitHandler(k.exitCode)
	})
}
```

Both new steps talk to the collector. `sdkmetric.MeterProvider.Shutdown` flushes through the `PeriodicReader`, `sdktrace.TracerProvider.Shutdown` drains the batcher, and `sdklog.LoggerProvider.Shutdown` (reached via `handlerOtel.Close`, `pkg/log/handler_otel.go:117`) drains the batch processor. Each export honors `otel.exporter.timeout` (10s) and then the retry budget `max_elapsed_time` (300s, `pkg/otel/settings.go:92`). `k.ctx` is the app root context — `appctx.WithContainer(context.Background())` in `application.New`, never cancelled — so nothing bounds the loop. A collector that accepts connections but stalls turns exit into a multi-minute hang, and the kernel's `kill_timeout` has already elapsed by the time `exit()` runs.

The `forceExit` interaction is the sharper edge. `killIfNotStopped` and the double-signal watcher both call `forceExit`, which calls `exit()`. If `exit()` is already inside a shutdown handler, `exitOnce.Do` returns immediately and the second signal is a no-op — the escape hatch for a stuck shutdown now depends on the very code that is stuck. Bounding the shutdown context and giving `forceExit` a path that bypasses the handlers restores the previous guarantee.

Handlers run in registration order (`metric`, then `tracing`) with the logger closed last, so shutdown diagnostics are still exportable; a failing handler does not stop the rest.

### Logger close reports success unconditionally

```go
for _, handler := range l.handlers {
	if closingHandler, ok = handler.(ClosingHandler); !ok {
		continue
	}

	if err := closingHandler.Close(ctx); err != nil {
		return nil
	}
}
```

Two effects: the OTLP log provider's shutdown error never reaches the caller, and the early return skips every handler after the failing one. With one closing handler today the leak is latent, but the contract is wrong the moment a second one is added. `errors.Join` accumulated across the full loop fixes both.

This is also why `TestKernelExitReportsLoggerCloseError` (`pkg/kernel/logger_close_test.go:34`) is green: it drives `k.exit()` with a hand-written `closeTestLogger` whose `Close` returns an error, so it validates the kernel branch while the real implementation can never trigger it. A test that runs `gosoLogger.Close` with a failing handler would have caught this.

### Flush depends on an option nobody adds

`metric.NewOtelWriter` (`pkg/metric/writer_otel.go:87`) and `newOtelTraceProvider` (`pkg/tracing/otel_trace_provider.go:92`) both register `provider.Shutdown` into appctx under a private key. `metric.NewShutdownHandler` and `tracing.NewShutdownHandler` pull it back out, and both are only wired by `application.WithOtelShutdown`:

```go
func WithOtelShutdown(app *App) {
	app.addKernelOption(func(config cfg.GosoConf) kernelPkg.Option {
		return kernelPkg.WithShutdownHandler(metric.NewShutdownHandler(), tracing.NewShutdownHandler())
	})
}
```

`Default()` (`pkg/application/app.go:38`) does not include it, and neither `WithTracing` nor `WithMetrics` implies it. The only caller in the tree is `examples/otel/main.go:68`. An app that enables the `otel` metric writer without the extra option keeps a `PeriodicReader` goroutine alive until process death and drops whatever accumulated since the last tick. Registering the handler from inside `WithTracing`/`WithMetrics` — where the provider is created — removes the footgun, and the handlers are already no-ops when nothing was registered.

The asymmetry with logs is worth noting: log export flushes reliably because `logger.Close()` is unconditional. Metrics and traces are the ones that need the opt-in.

### Kernel now needs a GosoLogger, and asserts for it

`BuildKernel`, `BuildFactory` and `NewFactory` changed from `log.Logger` to `log.GosoLogger`, and `GosoLogger` gained `Close(ctx)`. Both are source-breaking for external callers and external implementations.

The runtime edge is `pkg/kernel/kernel.go:87`:

```go
logger: logger.WithChannel("kernel").(log.GosoLogger),
```

`WithChannel` is declared to return `log.Logger`. `gosoLogger` and the test `loggerMock` happen to return values that satisfy `GosoLogger`, but nothing in the interface guarantees it — `SamplingLogger.WithChannel` (`pkg/log/logger_sampling.go:46`), for instance, returns a type without `Option`/`Close`. Any wrapper like that panics during `newKernel`. Storing the root `GosoLogger` for `Close` and a channel-scoped `log.Logger` for messages avoids the assertion entirely.

### Exporter settings accept configurations that quietly misbehave

`ReadSettings` unmarshals and returns; there is no validation pass. Three combinations fail silently rather than at boot:

`protocol: http` with the default `port: 4317` sends OTLP/HTTP at the gRPC port. The field comment documents the 4317/4318 convention but the default cannot follow it, so the mistake surfaces as export errors in the background handler.

`compression: snappy` (or any typo) falls through `gzipEnabled()` to no compression. Given the strict-placeholder philosophy documented in the repo's naming rules, silently degrading here is inconsistent.

A `tls.cert_file` without `tls.key_file` skips the `Certificates` assignment in `buildTLSConfig` (`pkg/otel/exporter.go:67`) and connects with server-only TLS. An operator who intended mTLS gets a working connection with the wrong identity — the worst kind of silent success. The rest of the TLS code is careful: `min_version` defaults to 1.3, the CA-append failure is a hard error, and `insecure_skip_verify` carries an explicit opt-in `nolint`.

On posture: `insecure: true` is the default and `headers` is the documented carrier for auth and tenant values (`pkg/otel/settings.go:63,69`). That combination puts bearer tokens on the wire in cleartext. A local-agent deployment makes the default defensible, but the code should refuse or warn when headers are configured on an insecure transport.

### Traces diverge from the shared exporter config

```go
exporterSettings := settings.Exporter
exporterSettings.Protocol = otel.ProtocolGrpc
```

`NewOtelGrpcTracer` overwrites the operator's protocol choice, and there is no exporter name that honors `otel.exporter.protocol`. Meanwhile `OtelSettings.Exporter` still defaults to `otel_http`, which reads the legacy `tracing.otel.http.*` block — so a config that fills in `otel.exporter.*` and forgets `tracing.otel.exporter: otel_grpc` produces traces going somewhere else entirely, with no error. `pkg/tracing/AGENTS.md` now shows `otel_grpc` in its example while the code default stays `otel_http`.

Propagator handling is stricter, and better for it: unknown names error out with the supported set listed (`pkg/tracing/otel_trace_provider.go:118`).

### Resource attributes

`BuildResource` returns `resource.NewWithAttributes(semconv.SchemaURL, attributes...)`. That bypasses `resource.Default()`, so `telemetry.sdk.name/language/version` are absent and `OTEL_RESOURCE_ATTRIBUTES` — the standard escape hatch operators expect — has no effect. `resource.Merge(resource.Default(), …)` keeps both, at the cost of handling the schema-URL conflict explicitly.

The error handling inside the function is asymmetric:

```go
if serviceNamespace, err := identity.Format(settings.ServiceNamespacePattern, settings.Delimiter); err == nil {
	attributes = append(attributes, semconv.ServiceNamespace(serviceNamespace))
}
```

A typo in `service_name_pattern` fails the build; the same typo in `service_namespace_pattern` drops `service.namespace` and starts silently. Custom attribute patterns propagate their errors, so the namespace case is the outlier.

Related config wart: `examples/otel/config.dist.yml:23` adds `deployment_environment: "{app.env}"` as a resource attribute with a comment explaining the underscore. The exported key is literally `deployment_environment`, which is not the semconv key, and `BuildResource` already sets `deployment.environment` from the identity — so the example emits a redundant non-standard attribute.

### Metric bridge

The instrument cache holds its mutex only around creation, not around `Add`/`Record`, and `effectiveKind` mirrors the prometheus writer's unit-based fallback so both writers classify identically.

What's lost in translation is the timestamp. `record` (`pkg/metric/writer_otel.go:133`) never reads `datum.Timestamp`, which `writer.go:55` populates for every datum. With `aggregate: true` the daemon hands over points describing a completed interval; those land at the next `PeriodicReader` tick instead. Combined with `metric.interval: 60s` and the writer's own `interval: 60s`, a point can be attributed up to two minutes late.

The appctx registration for the shutdown func is keyed by type, so a second `NewOtelWriter` in the same container silently drops its provider's `Shutdown` — the first registration wins and the second `MeterProvider` runs unmanaged. Unlikely in practice, silent when it happens.

On the recursion question: `Write` logs per-datum failures on the `metrics` channel, but a dead collector produces no errors there — instrument creation is local and export failures go to the OTEL global handler. `Emit` only enqueues, so an `otel` log handler cannot re-enter the export path.

### Log handler

The per-channel level cache moved verbatim out of `handlerIoWriter` into the shared `handlerBase`, so both handlers now behave identically for `log.handlers.<name>.channels.*`.

Two gaps. `handlerOtelFactory` builds the exporter with `context.Background()` at config-parse time, so a construction failure has no cancellation path and the resulting provider is only reachable through the logger — if kernel construction fails afterwards, the exporter leaks. And `HandlerOtelSettings` exposes only `level`, so the batch processor's queue size, export interval and timeout are fixed at SDK defaults with no way to tune them for a high-volume service.

`ClosingHandler` (`pkg/log/handler.go:19`) is the one new exported symbol without a doc comment, while its neighbours in the same file all have one.

### Test env and coverage

The `otel` test env component starts a real collector, points `otel.exporter.*` at it, and `otelcol.Client` parses the debug exporter's stdout to assert on received spans, metrics and log records.

Not tested: `metric.NewOtelWriter` and `handlerOtelFactory` (the suite constructs providers directly, so config-driven wiring, `getMetricWriterSettings` and the appctx shutdown registration never run); the kernel exit sequence against a real `gosoLogger`; any TLS or mTLS path in `buildTLSConfig`; `protocol: http` for any signal; and the retry/backoff behavior against an unreachable collector, which is the failure mode most likely to bite in production.

`OtelComponent.grpcHost`/`grpcPort` hand-roll the host/port split rune by rune where `net.SplitHostPort` would do, and the collector health check discards the response status by design (documented in a comment, since the OTLP receiver answers 404 at `/`).

### Bundled changes

Three edits are unrelated to OTEL: the `examples/integration/config.dist.yml` database credentials rename, the mailpit component's `from_address` switch to `example.com`, and a set of `config` → `_` parameter renames in `pkg/application/options.go` that are pure lint cleanup. `examples/otel/config.yaml` is committed next to `config.dist.yml` but referenced by neither `main.go` nor `run.sh`, and it disagrees with the dist file on app name and compression — it reads like a local scratch file that slipped in.

Root `AGENTS.md` still has no entry for `pkg/otel` in its domain map, though `pkg/otel/AGENTS.md` was added and `pkg/tracing/AGENTS.md` updated.

The log-signal dependencies pin at `v0.8.0` (`go.opentelemetry.io/otel/log`, `sdk/log`), which is pre-1.0 and still subject to breaking changes; the trace and metric pins are all `v1.32.0`. Worth stating explicitly in the release notes, since it constrains how the log handler's API can be presented as stable.
